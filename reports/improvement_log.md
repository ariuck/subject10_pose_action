## 3일차

### 1. 교재 18번 코드가 잘못 실려 있었다

- **문제**: 교재 본문의 `18_video_frame_features.py`가 17번 코드와 같은 내용이었다.
- **원인**: 교재 편집 오류로 보인다.
- **한 일**: 26번의 설명, 실행 예시, 출력 결과를 기준으로 코드를 직접 작성했다.
- **결과**: Total frames 60, Feature count 38로 교재 출력과 같게 나왔다.
- 근거: `README.md` Day 03

### 2. Confidence가 높은데 관절 위치가 틀렸다

- **문제**: `bend_pose.jpg`의 왼팔꿈치 각도가 155.81°로 나왔다. 그런데 사진을 보니 왼팔꿈치·손목이 실제 왼팔이 아니라 오른팔 위에 겹쳐 찍혀 있었다.
- **원인**: 측면 자세에서 가려진 반대쪽 팔을 YOLO가 보이는 팔 위에 찍었다. Confidence는 0.817 / 0.884로 높아서 기존 Confidence 검사로는 걸러지지 않았다.
- **한 일**: `12_joint_angle.py`에 겹쳐 찍힌 팔·다리 검사를 추가했다. 한쪽 관절이 반대쪽 팔(다리) 선에 거의 붙어 있으면(overlap < 0.05) Confidence가 낮은 쪽 각도를 SKIP 한다.
- **결과**: 3일차 이미지 8장 중 이 각도 하나만 SKIP 됐다(overlap 0.035).
- **배운 점**: Confidence가 높다고 위치가 맞는 것은 아니다. 측면 자세는 결과 이미지를 직접 확인해야 한다.
- 근거: `reports/day03/bend_pose_left_right_check.md`

### 3. 측면에서 어깨 폭 정규화가 크게 흔들렸다

- **문제**: 같은 눕기 자세인데 Near와 Far의 정규화 좌표 거리가 8.199로 크게 차이 났다.
- **원인**: 옆에서 보면 두 어깨가 겹쳐 어깨 폭이 18.99px까지 줄고, 그 값으로 나눈 좌표가 튀었다.
- **한 일**: 기준 길이를 상체 길이(어깨 중심~골반 중심)로 바꿔서 비교했다.
- **결과**:

| 비교 | 어깨 폭 기준 | 상체 길이 기준 |
|---|---:|---:|
| 눕기 Near / Far (같은 자세) | 8.199 | **0.438** |
| 눕기 vs 서기 (다른 자세) | 3.518 | **1.209** |

  같은 자세끼리는 차이가 작아지고, 다른 자세끼리는 차이가 커졌다. 그래서 이후 팀 Feature는 모두 상체 길이를 기준으로 계산했다.
- 근거: `reports/team_projects/team03/feature_expansion_log.md` 1단계

### 4. 관절각도로는 서기와 눕기를 구분하지 못했다

- **문제**: 무릎 각도가 서기 161~173°, 눕기 159~164°로 둘 다 펴져 있었다.
- **원인**: 관절각도는 얼마나 굽혔는지만 알려 주고, 몸이 세로인지 가로인지는 알려 주지 않는다.
- **한 일**: 팀 Feature 8개를 설계했다(`src/team_features.py`). 상체 기울기, 골반-발목 높이, BBox 비율, 속도 등이다.
- **결과**: 기절 영상에서 상체 기울기가 서기 7.1° → 누움 84.1° → 일어남 1.4°로 바뀌어 동작이 숫자로 보였다. 이것이 4일차 45-D의 출발점이 됐다.

## 4일차

### 5. 휴대폰 영상에서 대표 Frame 추출이 멈췄다

- **문제**: 교재 21번 코드가 End Frame을 읽지 못하고 멈췄다.
- **원인**: 휴대폰 영상은 영상 정보에 적힌 Frame 수가 실제보다 1~6개 많았다.
- **한 일**: 실제로 읽히는 마지막 Frame을 쓰도록 처리한 사본을 만들었다(`scripts/team3/team_extract_clip_keyframes.py`). 교재 원본은 그대로 두었다.
- **결과**: 36개 영상에서 대표 Frame 108장을 만들었다.

### 6. 정면·측면 영상 결과가 서로 덮어써졌다

- **문제**: 같은 동작의 정면·측면 영상이 같은 이름으로 저장됐다.
- **원인**: 22번 코드는 파일 이름을 `action_label`로 쓰기 때문에 같은 동작이면 이름이 같아진다.
- **한 일**: Label 뒤에 `_front` / `_side`를 붙였다(예: `kiosk_strike_front`).
- **결과**: 36개 Sequence가 모두 따로 저장됐다.

### 7. 속도 Feature가 관절 떨림 때문에 튀었다

- **문제**: 바로 앞 Frame과 비교한 속도는 바닥 동작에서 p95가 20~40까지 튀었다.
- **원인**: 60fps에서는 Frame 사이 시간이 짧아, 관절 좌표의 작은 떨림이 큰 속도로 계산됐다.
- **한 일**: 0.1초(6 Frame) 간격으로 비교하고, 영상마다 상체 길이 중앙값으로 나눴다.
- **결과**: 동작별 차이가 보이게 됐다. 측면 기준으로 던지기 손목 속도 p95 9.51, 앞차기 발목 속도 p95 6.64가 나와 다른 서서 하는 동작보다 높았다.

### 8. 강사님 추천 Feature 중 하나를 계산할 수 없었다

- **문제**: 강사님이 3팀에 추천한 "양발과 문 사이 거리"를 만들 수 없었다.
- **원인**: 촬영 장소가 강의실이라 화면에 문·키오스크·냉동고가 없었다.
- **한 일**: 우리 17개 동작에는 손을 빠르게 쓰는 이상행동이 6개 있다. 그래서 강사님 표의 "좌·우 손목 속도 +2"로 대체했다.
- **결과**: 38-D + 7개 = 45-D를 완성했다. 물체와의 거리는 영상(또는 ROI)이 생기면 다시 넣을 항목으로 남겼다.

### 9. 일부 영상의 파일 순서가 반대였다

- **문제**: S03·S05의 A009(엎드려 폰보기)는 정면·측면 파일 순서가 바뀌어 있었다.
- **원인**: 촬영할 때 측면을 먼저 찍었다.
- **한 일**: 사람별 대표 장면 모음을 보고 바로잡았다.
- **결과**: 170개 영상의 Label·방향이 모두 맞는 것을 확인했다.

### 10. 영상 정보와 실제 Frame 수가 달랐다

- **문제**: 영상 정보의 Frame 수는 70,621개인데 실제로 읽힌 Frame은 70,159개였다.
- **한 일**: 실제로 읽힌 Frame만 사용했다.
- **결과**: 그중 Pose 성공 69,926(99.7%), 45-D 성공 68,813.

## 5일차

### 11. 교재 26번 코드가 상대경로에서 오류를 냈다

- **문제**: `--video-root`에 상대경로를 넣으면 `relative_to(ROOT)`에서 ValueError가 났다.
- **한 일**: 교재 원본은 그대로 두고, 3팀 사본에서만 경로를 프로젝트 기준으로 바꾸도록 고쳤다.
- **결과**: 3팀 영상 170개 Keypoint를 모두 추출했다.

### 12. 자동 QA에서 CHECK가 5개 나왔다

- **문제**: S02의 A001~A005가 한 사람 비율(single_person_ratio) 기준에 걸려 CHECK가 됐다.
- **한 일**: 원본 영상을 직접 확인했다.
- **결과**: 옷걸이에 걸린 외투를 두 번째 사람으로 잘못 검출한 것이었다. 촬영 대상은 정상이어서 5개 모두 PASS로 판정했다.
- **배운 점**: 자동 QA는 후보를 좁혀 줄 뿐이고, 최종 판단은 원본을 보고 사람이 한다.

### 13. 처음에는 승인된 Clip이 5개뿐이었다

- **문제**: 29번을 실행하니 승인 목록에 Clip이 5개만 들어갔다.
- **원인**: 교재 28·29번은 모든 Clip에 `human_decision`이 있어야 하고, 그중 PASS만 승인한다. AUTO_PASS도 사람이 확인해야 한다는 뜻이다.
- **한 일**: AUTO_PASS 13개도 영상을 직접 보고 PASS로 기록했다.
- **결과**: 18개가 모두 승인됐다.

### 14. 3팀 측면 영상이 QA에서 불리하게 걸렸다

- **문제**: 측면은 반대쪽 팔다리가 가려져 중요 관절 저신뢰도 기준에 걸리기 쉬웠다.
- **한 일**: 판단을 돕는 참고 열 3개를 추가했다. 연속 Pose 누락 최대 시간, 정규화 기준 관절(어깨·골반) 저신뢰도 비율, 더 잘 보이는 쪽 관절의 저신뢰도 비율이다. 중요 관절도 3팀 동작에 맞게 다시 정했다.
- **결과**: AUTO_PASS 166, CHECK 4가 나왔다. 예를 들어 S02_A002_T02는 "보이는 쪽 팔 저신뢰도 0%"로 원인이 바로 설명됐다. 4개 모두 원본을 확인해 PASS로 판정했고, 그중 2개(S04_A010_T01, S05_A017_T02)는 재촬영 후보로 남겼다.
- 근거: `reports/team_projects/team03/team03_data_preparation_report.md` 4장

### 15. Frame을 무작위로 나누면 정답이 새어 나갔다

- **문제**: 32번 실험에서 Frame을 무작위로 나누자 Train과 Test에 같은 사람 3명, 같은 Clip 18개가 모두 겹쳤다.
- **한 일**: 사람(Subject) 단위로 나눴다(S01 Train / S02 Validation / S03 Test). 3팀은 S01~S03 / S04 / S05로 나눴다.
- **결과**: 31번 검사에서 Leakage check: OK가 나왔다. 3팀은 17개 동작이 모든 Split에 들어 있는 것도 확인했다.

## 6일차

### 16. 검증 결과가 교재와 달랐다

- **문제**: Validation Accuracy가 교재는 0.6667인데 우리는 0.5000이었다.
- **한 일**: 입력 Keypoint, Sequence의 유효 Frame 수, Static 결과, 좌표만 결과를 단계별로 교재와 비교했다.
- **원인**: 다른 결과는 모두 같았고, S02 wave 한 Clip만 달랐다. 이 Clip은 drink_return과 wave의 투표가 0.22로 거의 동점이었다. 라이브러리 버전·GPU 차이로 생긴 아주 작은 좌표 차이가 동점을 뒤집었다.
  - 우리: ultralytics 8.4.214, torch 2.15, RTX 3060
  - 교재: ultralytics 8.4.138, torch 2.14, RTX 4080 SUPER
- **결과**: 코드 문제가 아니라는 것을 확인했다. Validation이 6개라 Clip 하나가 Accuracy를 0.17씩 바꾼다는 것도 확인했다.
- 근거: `reports/day06/day06_summary.md` 4장

### 17. 교재 6일차 코드는 3팀 데이터에 그대로 쓸 수 없었다

- **문제**: 34~40번 코드 안에 경로와 "6개 Action / Clip 6개"가 고정되어 있었다.
- **한 일**: 교재와 같은 공통 함수(`src/sequence_utils.py`)와 같은 모델 설정(`configs/day06_baseline.json`)을 불러오는 3팀 실행 파일 하나를 만들었다(`scripts/team03/team_day06_baseline.py`).
- **결과**: 같은 계산 방식으로 17개 동작 170개 Clip을 학습·평가했다.

### 18. 팔로 하는 동작끼리 혼동했다

- **문제**: 38-D Baseline은 Validation 34개 중 9개를 틀렸다. 대부분 내려치기·던지기·휘두르기·밀치기·흔들기처럼 서서 팔을 쓰는 동작끼리였다.
- **한 일**: 한 번에 한 조건만 바꿔 비교했다. 조건을 고르는 기준(Validation Macro F1 최고)은 Test를 보기 전에 정했다.

| 조건 | Validation Accuracy | Macro F1 |
|---|---:|---:|
| 38-D (교재) | 0.7353 | 0.7373 |
| **45-D (팀 Feature)** | 0.7647 | **0.7725** |
| 동작 구간만 | 0.7941 | 0.7588 |
| 정면만 / 측면만 | 0.6471 | 0.5882 / 0.5529 |

- **결과**: 45-D를 선택했다. 처음 보는 사람(S05) Test에서 **0.6765 → 0.7647**(23 → 26개 정답)로 올랐다. Validation(+1개)보다 Test(+3개)에서 더 크게 좋아졌다.
- **남은 문제**: 밀치기와 흔들기는 끝까지 구분하지 못했다(F1 0). 손이 무엇에 닿는지(물체 위치) 정보가 필요하다.
- 근거: `reports/day06/challenge/mini_challenge_result.md`

### 19. Feature를 늘린다고 항상 좋아지지는 않았다

- **문제**: 45-D가 좋아졌지만, 7개 중 어떤 Feature가 도움이 됐는지는 알 수 없었다.
- **한 일**: Feature를 한 단계씩 늘려 Validation으로 비교했다.

| 단계 | Feature | Accuracy | Macro F1 |
|---|---:|---:|---:|
| 교재 | 38 | 0.7353 | 0.7373 |
| + 자세 3개 | 41 | 0.7647 | 0.7647 |
| + 발목 속도 | 43 | **0.7941** | **0.7922** |
| + 손목 속도 | 45 | 0.7647 | 0.7725 |

- **결과**: 손목 속도를 넣자 오히려 조금 낮아졌다. 팔 동작은 모두 손목이 빠르게 움직여서 서로를 구분하는 데 도움이 안 됐다. 이 동작들은 Feature 중요도는 높았지만 성능을 올리지는 못했다.
- **결정**: Test를 이미 본 뒤라 최종 조건은 바꾸지 않았다. 43-D는 데이터가 늘어나면 다시 비교할 후보로 남겼다.
